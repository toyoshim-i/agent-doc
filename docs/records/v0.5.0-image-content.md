# ADR: Multimodal Image Content in v0.5.0

This record documents the architectural decision made in `agent-man` v0.5.0 to support multimodal image content in MCP tool responses. For active library usage, see the [Embedding Guide](../guides/embedding.md) or the [agent-man Overview](../overview.md).

## Context & Problem

Host applications such as Karakuri need MCP tools that render visual shader outputs and return them directly to multimodal LLMs so agents can inspect and iterate on visual results.

Placing base64 strings inside `structuredContent` does not work because MCP clients treat `structuredContent` as raw text/JSON rather than visual model input. Multimodal MCP clients expect standard image content blocks in `result.content`:

```json
{ "type": "image", "data": "<base64>", "mimeType": "image/png" }
```

## Decision

1. **Convert `ToolContent` from a struct into a tagged enum**:
   ```rust
   #[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
   #[serde(tag = "type", rename_all = "snake_case")]
   #[non_exhaustive]
   pub enum ToolContent {
       Text { text: String },
       Image {
           data: String,
           #[serde(rename = "mimeType")]
           mime_type: String,
       },
   }
   ```
   Using a tagged enum prevents invalid states (such as an image item carrying meaningless `text` fields) and uses `#[non_exhaustive]` so future MCP content types (`audio`, `resource_link`) can be added cleanly.

2. **Ergonomic constructors and helpers**:
   - `ToolContent::image(data_base64, mime_type)` automatically strips optional `data:<mime>;base64,` URL prefixes.
   - `ToolResult::image(...)` and `ToolResult::text_and_image(...)` allow returning single-line multimodal responses.
   - `ToolResult::text_content()` joins all text blocks with `\n` while skipping image blocks.
